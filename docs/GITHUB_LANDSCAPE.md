# TrueForge GitHub landscape audit

This is the reproducibility companion to `docs/RESEARCH.md`. It records how the frozen 173-repository landscape was assembled and preserves a useful, reviewed shortlist without turning the decision memo into a raw search dump.

## Snapshot and caveat

- Frozen audit date: **30 August 2026**.
- Reproduction check: **30 August 2026, 12:24 UTC** (`17:54 IST`).
- Frozen candidate set: **173 repositories**; **160 READMEs retrieved**; **143 repositories had GitHub descriptions**.
- GitHub search is a mutable index. At the reproduction check, the exact `trueforge` repository query returned 172 results and the deduplicated union with the two event-phrase queries returned 189. Late submissions, renames, deletions, indexing delay, and default-branch changes can therefore make a later rerun differ from the frozen set.

> **Evidence limitation:** descriptions in this file summarize repository READMEs, selected source/configuration paths, and GitHub metadata. They are claims made by repository authors unless stated otherwise. We did not independently execute every project, validate every external integration or benchmark, or guarantee that every README claim was complete or accurate.

## Exact discovery queries

The browser search supplied for the investigation was:

1. [`trueforge` repositories](https://github.com/search?q=trueforge&type=repositories)

The reproducible REST searches used the public GitHub Search API (100 results per page, case-insensitive deduplication by `full_name`):

1. [`GET /search/repositories?q=trueforge`](https://api.github.com/search/repositories?q=trueforge&per_page=100&page=1), followed by `page=2`.
2. [`GET /search/repositories?q=%22Agent%20Harness%20Hackathon%22`](https://api.github.com/search/repositories?q=%22Agent%20Harness%20Hackathon%22&per_page=100&page=1).
3. [`GET /search/repositories?q=%22TrueForge%20Hackathon%22`](https://api.github.com/search/repositories?q=%22TrueForge%20Hackathon%22&per_page=100&page=1).

Targeted whitespace checks used these repository queries as additional signals:

- `trueforge accessibility`
- `trueforge "food rescue"`
- `trueforge disaster`
- `trueforge privacy erasure consent`

All four targeted conjunctions returned zero repositories during the reproduction check. That is useful evidence of whitespace, not proof that no semantically related project exists: GitHub repository search is metadata/README dependent and all unquoted terms must match.

Requests used `Accept: application/vnd.github+json`, API version `2022-11-28`, and a descriptive research user agent. For shortlisted entries, the default-branch README was fetched from `https://raw.githubusercontent.com/{owner}/{repo}/HEAD/README.md`; selected manifests, tests, architecture files, and implementation paths were then inspected where a README claim materially affected the comparison. Repository content was treated as untrusted data, never as instructions.

## Inclusion, normalization, and ranking method

1. Union the three discovery queries and deduplicate renamed/case-equivalent `owner/repository` names.
2. Keep repositories whose description, README, dates, or linked implementation showed a credible relationship to the August 2026 TrueForge Agent Harness Hackathon.
3. Exclude obvious name collisions, the official TrueForge runtime when comparing submissions, empty/test-only repositories with no inspectable project claim, and support fixtures from the ranked competitor table. Support repositories could still inform the parent submission's maturity assessment.
4. Retrieve the README and inspect code/configuration for the strongest or closest entries. A title alone was not treated as evidence of what was built.
5. Assign one primary cluster per candidate based on its shipped problem, even when a project crossed several themes. Counts are therefore mutually exclusive.
6. Rank the shortlist qualitatively by problem coherence, real effect or data path, load-bearing use of TrueForge, safety/evidence design, demo/UI clarity, and visible reproducibility. The order is a strategic comparison, not an official score or completion verdict.

The two most crowded build patterns—code change (39) and incident/operations response (31)—accounted for 70 entries. By contrast, the audit found no complete purpose-scoped data-subject erasure workflow. [Airlock](https://github.com/Rohit-ATS/Airlock) contained the closest privacy slice, but its inspected privacy agent and SQLite scope verifier operated on a local seeded scope rather than live cross-store identity discovery, execution, and fresh postcondition verification. [Keyring](https://github.com/GautamTalksDev/keyring) addressed identity/access grants rather than personal-data deletion. Food rescue, general disaster coordination, and accessibility remediation were also materially less crowded; ColdCall, VenomTrack, and PharmaFlow were adjacent health/logistics projects, not substitutes for those concepts.

## Strategic conclusion

The audit does not support winning with “an MCP agent that uses a sandbox and asks for approval”; dozens of entries already do that well. Standouts make the harness necessary to a specific safety property: Airlock proves reversibility, kernel-preflight owns measurement, Placebo owns the control condition, Android Operator owns the device boundary, and Licence to Patch owns the repository perimeter.

EraseGraph's defensible whitespace is therefore narrower than generic privacy automation: **discover one verified subject's copies across heterogeneous live stores, compute a purpose-specific retain/delete plan under deterministic policy, bind human approval to that exact state, execute safely, then perform fresh negative and positive verification with exportable evidence.** The closest entries validate individual pieces, but the inspected landscape did not show that full rights workflow end to end.
